Not a linter. A ratchet for ESLint.

Keep the rules on.
Make lint debt only go down.

ESLint finds the violations. RatchetStrap compares them with a baseline you commit, so a new violation fails the build and a repaired one has to be removed from the file.

A file you can read in a review, instead of a sweep you never finish or a rule you switch off within a week.

Two things that used to slip through.

RatchetStrap ships none of these rules; ESLint does the detection. These are the findings a warning-only setup never fixes, and they are what the baseline is for. No ESLint, nothing to ratchet.

01 · derived statehouse/no-derived-effect
before
// effect derives state from props
const [fullName, setFullName] = useState("");
useEffect(() => {
  setFullName(`${first} ${last}`);
}, [first, last]);
check
added  house/no-derived-effect
       src/profile.tsx:...#1
exit 1  new debt

The rule is on and the baseline has no allowance for this identity, so the gate exits 1. A disable comment moves it to suppressed messages, where it still counts.

after
const fullName = `${first} ${last}`;

One render, no stale frame. If the finding had been baselined, tighten --write would remove the now-stale entry.

02 · implicit statehouse/explicit-state-machine
before
const [loading, setLoading] = useState(false);
const [error, setError] = useState<Error | null>(null);
const [data, setData] = useState<Data | null>(null);
check
added  house/explicit-state-machine
       src/order.tsx:...#1
exit 1  new debt

loading && error is representable today. The rule is only a warning until the ratchet holds it.

after
type OrderState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "ready"; data: Data }
  | { status: "failed"; error: Error };

Four states instead of eight combinations; impossible states are unrepresentable. Old baseline entries become stale until tightened.

The rule IDs are house-rule names, not detectors bundled here. Any ESLint rule works; RatchetStrap makes the new finding fail, the repair visible, and the suppression count.

A red check is easy to make green.

Coding agents are good at it: mock the thing under test, retry the flake, raise the timeout, add an eslint-disable. Every one of those passes CI. RatchetStrap makes the honest path the one that also passes.

  • 01

    Baseline, not sweep

    Accept today's violations once, in a file you commit. Keep the rule on.

  • 02

    Only goes down

    An entry that no longer appears is a stale allowance, and it fails the gate too.

  • 03

    Suppressed still counts

    A disabled or suppressed diagnostic is debt. It is not an exemption from debt.

  • 04

    Cannot be raised

    The baseline is compared with a trusted revision, so debt grows only through a reviewed edit.

zsh — ratchet-strap
$ ratchet-strap init --rules no-console,complexity --exec-eslint
$ ratchet-strap check --exec-eslint
exit 1 — new violation, stale entry
$ ratchet-strap tighten --exec-eslint --write
$ ratchet-strap check --exec-eslint
exit 0 — clean

Output abridged. Every command prints JSON.

How it works

A Node script: spawn your ESLint, build one identity string per diagnostic, set-diff against the committed baseline. No model calls, no network, no source parsing.

  1. Turn the rules on

    Enable the ESLint rules you want to ratchet in your flat config.

  2. Record what exists

    init writes today's diagnostics to .ratchet-strap.json. Nothing is fixed, nothing is swept.

  3. Check on every run

    check reruns your ESLint scope and never writes. CI runs the same command.

  4. Claim the fixes

    tighten --write removes the entries you repaired. Leaving one behind keeps failing.

Identities, not line numbers

An identity is the relative file, the rule id, the diagnostic message and the occurrence number. Line and column are not part of it, so moving unchanged code within its file does not invalidate the baseline.

  • That is diagnostic, not semantic. A rename or a message change may need a reviewed migration.
  • Count profiles are weaker by design: one repaired violation can offset a new one of the same rule anywhere in scope.
  • Suppressed messages join the same numbering, so silencing one does not remove it.
  • RatchetStrap never downloads ESLint, edits your config or repairs a violation.
baseline.ratchet-strap.json
{
  "schemaVersion": 2,
  "mode": "identities",
  "adapter": "eslint-identities@1",
  "identities": {
    "max-params": [
      "app/mail.js:max-params:Function 'sendMessage' has too
       many parameters (6). Maximum allowed is 5.#1"
    ]
  }
}

Your thresholds, not ours

The engine is opinion-free. Limits, named profiles, enabled golden rules and adoption recipes live in a house-rules/ directory your repository owns and reviews.

A package upgrade cannot change your limits, your enabled profiles or your exclusions. Only an edit you review can.

setuptwo commands
$ cp -R node_modules/ratchet-strap/house-rules ./house-rules
$ ratchet-strap rules --house-rules ./house-rules/index.mjs

Edit quality.mjs and golden.mjs, then keep the directory in version control.

Profiles

A profile selects a comparison mode and an adapter. New projects use eslint@1; a project that already has a count budget can adopt eslint-counts@1 deliberately.

ProfileAdapterComparison
eslint@1 defaulteslint-identities@1New and stale identities fail
eslint-counts@1eslint-json@1Per-rule warning and suppressed counts cannot grow

Baselines pin their adapter, so check and tighten infer the profile. Unknown versions and mixed modes fail; there is no implicit conversion between counts and identities.

The twelve defaults

Rules that hold in any repository, any language, any framework. Golden profiles are opt-in and supplied by your house rules; the engine ships none.

  • U1

    A change that adds a tracked violation fails the gate.

  • U2

    A baseline may only lose entries. Never raise one to make a change pass.

  • U3

    A suppressed or disabled diagnostic still counts as a violation.

  • U4

    A repaired violation must be removed from the baseline.

  • U5

    Every exemption is scoped to one rule, one location and one written reason.

  • U6

    One local command runs exactly the same checks as CI.

  • U7

    Generated artefacts reproduce with no diff.

  • U8

    Every gate has a fault and a control fixture proving both directions.

  • U9

    No secret value reaches a response, log, span, error or built artefact.

  • U10

    A published change carries a version bump and a changelog line.

  • U11

    A shared module mock keeps the real export surface.

  • U12

    Guarded code cannot opt out of the gate that guards it.

U1–U4 are enforced by this engine. U5 and U12 are review. The rest are consumer gates; the README names the mechanism for each.

Start with three commands

Your ESLint setup stays where it is. RatchetStrap records what it already reports, then holds the line.

Read the docs npm package

Exit codes: 0 passed, 1 violations or new debt, 2 invalid input or tool failure.

quickstartbash
$ ratchet-strap rules
$ ratchet-strap init --rules no-console,complexity --exec-eslint
$ ratchet-strap check --exec-eslint

After repairing debt: ratchet-strap tighten --exec-eslint --write. After enabling another rule: add --rules no-alert.
